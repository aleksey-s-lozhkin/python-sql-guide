JOIN: кардинальность важнее синтаксиса Кто с кем соединяется, сколько строк получится и куда исчезают NULL

JOIN отвечает на вопрос «какие строки двух таблиц относятся друг к другу». Синтаксис заучивается за минуту; сложность — в количестве строк и в NULL-ключах. Здесь — все типы соединений, кардинальность и точный вывод psql на learning_shop.

Самое главное
  • JOIN сопоставляет строки по условию ON: INNER оставляет только совпадения, LEFT — все левые, RIGHT — все правые, FULL — все с обеих сторон.
  • Число строк решает кардинальность: many-to-one (заказы → пользователи) строки сохраняет, many-to-many — перемножает. Сначала кардинальность, потом синтаксис.
  • NULL-ключ не соединяется ни с чем: заказ с user_id IS NULL выпадает из INNER JOIN. «Строки без пары» ищут через LEFT JOIN … IS NULL или NOT EXISTS.

01Что это и как читается

Соединение берёт строку из одной таблицы и ищет ей пару во второй по условию ON. Что делать с найденными и ненайденными — определяет тип соединения. Поэтому запрос читают не как «приклеить», а как «какие строки останутся и сколько их будет».

Соединение — это не обязательно две таблицы: можно соединить три и больше, а также таблицу с самой собой. На каждом шаге число строк может сохраниться, вырасти или уменьшиться, и это главный источник ошибок в отчётах.

Держите эту картинку в голове

JOIN — это склейка двух списков по номеру. У каждой строки слева ищется строка справа с тем же ключом. Нашлась — склеили; не нашлась — зависит от типа join.

Опасность не в склейке, а в количестве. Если ключ справа встречается дважды, одна строка слева даст две склеенные. Если дважды с обеих сторон — четыре. Это и есть кардинальность. Ту же метафору разбирает глава 16 — там это соединение в pandas.

03Синтаксис-шаблон

Базовая форма: SELECT … FROM a JOIN b ON условие. Условие ON — не фильтр результата, а правило сопоставления строк; его отсутствие даёт декартово произведение.

ref_sql_join_lab.sqlsql
SELECT o.id AS order_id, u.name, o.quantity
FROM orders o
JOIN users u ON u.id = o.user_id
ORDER BY o.id;
order_id | name | quantity ----------+-------+---------- 1 | Anna | 1 2 | Ivan | 2 3 | Anna | 3 4 | Olga | 1 5 | Ivan | 1 6 | Maria | 5 7 | Anna | 2 9 | Olga | 1 10 | Petr | 1 (9 rows)

Десять заказов дали девять строк: у заказа id = 8 ключ user_id IS NULL, и пара для него не нашлась. Алиасы o и u — не украшение: с ними условие читается однозначно.

ON или USING

USING (col) короче, но требует одинаковых имён колонок с обеих сторон. В learning_shop ключи названы по-разному — orders.user_id и users.id, — поэтому здесь только ON.

05Разбор по вариантам

Все примеры страницы — в файле ref_sql_join_lab.sql. База та же: learning_shop, PostgreSQL 14.

LEFT JOIN: все заказы

ref_sql_join_lab.sqlsql
SELECT o.id AS order_id, u.name, o.quantity
FROM orders o
LEFT JOIN users u ON u.id = o.user_id
ORDER BY o.id;
order_id | name | quantity ----------+-------+---------- 1 | Anna | 1 2 | Ivan | 2 3 | Anna | 3 4 | Olga | 1 5 | Ivan | 1 6 | Maria | 5 7 | Anna | 2 8 | | 1 9 | Olga | 1 10 | Petr | 1 (10 rows)

Теперь десять строк: заказ 8 остался, а имя пустое — NULL в колонках правой таблицы означает «пары не нашлось». Именно так LEFT JOIN сохраняет левую сторону.

RIGHT и FULL: сколько строк

ref_sql_join_lab.sqlsql
SELECT 'inner' AS join_type, COUNT(*) AS rows
FROM orders o JOIN users u ON u.id = o.user_id
UNION ALL
SELECT 'left', COUNT(*)
FROM orders o LEFT JOIN users u ON u.id = o.user_id
UNION ALL
SELECT 'right', COUNT(*)
FROM orders o RIGHT JOIN users u ON u.id = o.user_id
UNION ALL
SELECT 'full', COUNT(*)
FROM orders o FULL JOIN users u ON u.id = o.user_id
ORDER BY join_type;
join_type | rows -----------+------ full | 10 inner | 9 left | 10 right | 9 (4 rows)

INNER и LEFT различаются на одну строку — тот самый заказ без пользователя. RIGHT здесь совпал с INNER: у всех пяти пользователей есть заказы, поэтому «правых без пары» нет. FULL оставил и заказ без пользователя, и (если бы были) пользователей без заказов.

NULL-ключ не соединяется

ref_sql_join_lab.sqlsql
SELECT id, user_id
FROM orders
WHERE user_id IS NULL;

SELECT COUNT(*) AS matched_rows
FROM orders o
JOIN users u ON u.id = o.user_id;

SELECT o.id AS order_id
FROM orders o
WHERE NOT EXISTS (
    SELECT 1
    FROM users u
    WHERE u.id = o.user_id
)
ORDER BY o.id;
id | user_id ----+--------- 8 | (1 row) matched_rows -------------- 9 (1 row) order_id ---------- 8 (1 row)

Заказ 8 существует и содержит NULL в ключе. Но NULL = NULL — UNKNOWN, а не TRUE, поэтому соединение по NULL-ключу невозможно. Тот же ответ даёт NOT EXISTS — anti-join без соединения. В SQL это не баг, а следствие трёхзначной логики; в pandas NaN в ключе, наоборот, соединяется с NaN (глава 16).

semi-join через EXISTS

ref_sql_join_lab.sqlsql
SELECT u.name
FROM users u
WHERE EXISTS (
    SELECT 1
    FROM orders o
    JOIN products p ON p.id = o.product_id
    WHERE o.user_id = u.id AND p.category = 'electronics'
)
ORDER BY u.name;

SELECT u.name
FROM users u
JOIN orders o ON o.user_id = u.id
JOIN products p ON p.id = o.product_id
WHERE p.category = 'electronics'
ORDER BY u.name, o.id;
name ------ Anna Ivan Olga Petr (4 rows) name ------ Anna Ivan Olga Olga Petr (5 rows)

Обе строки отвечают на вопрос «кто покупал электронику», но по-разному. EXISTS возвращает каждого пользователя один раз — это semi-join. Обычный JOIN даёт по строке на каждый заказ, поэтому Olga с двумя электронными заказами появляется дважды. Если нужен только факт, берите EXISTS.

self-join и CROSS JOIN

ref_sql_join_lab.sqlsql
SELECT a.name AS user_a, b.name AS user_b, a.city
FROM users a
JOIN users b ON a.city = b.city AND a.id < b.id
ORDER BY a.name, b.name;

SELECT COUNT(*) AS cross_rows
FROM orders
CROSS JOIN users;
user_a | user_b | city --------+--------+-------- Anna | Olga | Москва (1 row) cross_rows ------------ 50 (1 row)

Self-join соединяет таблицу с самой собой: нашли пару «из одного города» — Anna и Olga. Условие a.id < b.id убирает зеркальные пары и пары с собой, а a.city = b.city не срабатывает для NULL — снова UNKNOWN. CROSS JOIN даёт 10 × 5 = 50 строк: декартово произведение, почти всегда признак забытого условия.

Фильтр в ON или в WHERE

ref_sql_join_lab.sqlsql
SELECT o.id AS order_id, u.name
FROM orders o
LEFT JOIN users u ON u.id = o.user_id
WHERE u.city = 'Москва'
ORDER BY o.id;

SELECT o.id AS order_id, u.name
FROM orders o
LEFT JOIN users u ON u.id = o.user_id AND u.city = 'Москва'
ORDER BY o.id;
order_id | name ----------+------ 1 | Anna 3 | Anna 4 | Olga 7 | Anna 9 | Olga (5 rows) order_id | name ----------+------ 1 | Anna 2 | 3 | Anna 4 | Olga 5 | 6 | 7 | Anna 8 | 9 | Olga 10 | (10 rows)

Первый запрос оставил только заказы Анны и Ольги — 5 строк: фильтр в WHERE применяется после соединения и отбрасывает NULL-строки, то есть LEFT фактически превращается в INNER. Второй — сохранил все 10 заказов: условие в ON решает, кого соединять, но левую сторону не выбрасывает.

Выручка по товарам

       SUM(o.quantity) AS units,
       SUM(o.quantity * p.price) AS revenue
FROM orders o
JOIN products p ON p.id = o.product_id
GROUP BY p.id, p.name, p.category
ORDER BY revenue DESC;
name | category | units | revenue ---------+-------------+-------+----------- Ноутбук | electronics | 2 | 150000.00 Монитор | electronics | 2 | 44000.00 Кофе | food | 8 | 3600.00 Книга | books | 3 | 2700.00 Мышь | electronics | 1 | 1500.00 Чай | food | 2 | 600.00 (6 rows)

Соединение даёт строку на заказ, GROUP BY сворачивает их в товары, SUM считает выручку. Заказ с NULL-ключом здесь не теряется: товар у него есть, а соединение идёт по product_id.

07Пять ошибок, на которых спотыкаются

Условие на правую таблицу в WHERE

LEFT JOIN … WHERE u.city = 'Москва' отбрасывает строки, где справа NULL, и фактически превращает LEFT в INNER. Левая сторона «исчезает» незаметно.

Нужны все левые строки — переносите условие в ON; нужен фильтр результата — оставляйте в WHERE осознанно.
Дубли из-за кардинальности

Соединение many-to-many перемножает строки: 2 слева × 2 справа = 4. Отчёт «внезапно» вырастает, а DISTINCT скрывает симптом, но не причину.

Проверить уникальность ключа (GROUP BY … HAVING COUNT(*) > 1), предварительно агрегировать сторону, которая размножает.
Ожидание, что NULL-ключ соединится

Заказ с user_id IS NULL не появится в INNER JOIN: NULL = NULL — UNKNOWN, а не TRUE.

Решить явно: исключить такие строки (WHERE user_id IS NOT NULL) или сохранить через LEFT JOIN.
Забытое условие соединения

FROM orders, users или CROSS JOIN без ON даёт декартово произведение: 10 × 5 = 50 строк вместо 10.

Всегда ON/USING; сверять число строк до и после соединения.
Фильтр до и после соединения — не одно и то же

Условие в ON фильтрует правую таблицу до сопоставления, условие в WHERE — результат после. Для LEFT JOIN это разные ответы.

Сначала сформулировать вопрос словами: «все заказы» или «только заказы москвичей» — и выбирать место условия.

08Мини-проверка

Пять вопросов и две задачи. Сначала своя попытка — потом спойлер.

Чем INNER JOIN отличается от LEFT JOIN?

INNER оставляет только строки, для которых нашлась пара. LEFT сохраняет все строки левой таблицы, подставляя NULL там, где пары нет.

Резюме: INNER — только совпадения, LEFT — все левые.
Почему заказ id = 8 не появляется в INNER JOIN с users?

У него user_id IS NULL, а соединение ищет равенство ключей. NULL = users.id даёт UNKNOWN, а не TRUE — пара не находится. В LEFT JOIN строка останется с NULL в колонках пользователя.

Резюме: NULL-ключ не равен ничему, даже другому NULL.
Что такое кардинальность и почему many-to-many опасен?

Это отношение числа строк: one-to-one, many-to-one, one-to-many, many-to-many. При many-to-many каждая пара совпавших строк даёт отдельную строку результата, поэтому строки перемножаются, а не «добавляются».

Резюме: сначала предскажите число строк, потом пишите JOIN.
Чем semi-join (EXISTS) отличается от обычного JOIN?

EXISTS проверяет факт существования пары и не размножает строки. Обычный JOIN выдаёт строку на каждое совпадение, поэтому пользователь с двумя заказами появится дважды.

Резюме: нужно «есть ли» — EXISTS; нужны детали — JOIN.
Как найти строки без пары?

Через anti-join: LEFT JOIN … WHERE right.id IS NULL. Альтернатива — NOT EXISTS; она безопаснее, когда в ключах есть NULL.

Резюме: anti-join ищет «сирот».

09Мостик: то же соединение в pandas

merge: how вместо типа JOIN

мост в pandaspython
import pandas as pd

orders = pd.read_sql("SELECT * FROM orders", conn)
users = pd.read_sql(
    "SELECT id AS user_id, name AS user_name, city FROM users", conn
)
products = pd.read_sql(
    "SELECT id AS product_id, name AS product_name, price FROM products", conn
)

left = orders.merge(users, on="user_id", how="left")          # LEFT JOIN
both = left.merge(products, on="product_id", how="inner")     # + INNER JOIN
both["total"] = both["quantity"] * both["price"]

only_orders = left[left["user_name"].isna()]                  # anti-join
has_user = orders.merge(users, on="user_id", how="inner",
                        validate="many_to_one")               # semi/many-to-one check

how="left" — это LEFT JOIN, how="inner" — INNER, validate="many_to_one" — проверка кардинальности, которую в SQL делают запросом GROUP BY … HAVING COUNT(*) > 1. После left join пропуски справа становятся NaN — с ними работают методы из главы 17.

Одно отличие, которое ломает отчёты

В SQL NULL-ключ не соединяется ни с чем; в pandas NaN в ключе считается равным NaN. При переносе запроса в pandas число строк может измениться — сверяйте его на каждом шаге (глава 16).
