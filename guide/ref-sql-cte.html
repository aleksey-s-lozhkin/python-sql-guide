Подзапросы и CTE: разложить вопрос Подзапросы, IN и EXISTS, WITH и рекурсия в PostgreSQL 14

Сложный отчёт почти никогда не пишется одним куском: сначала считают, потом фильтруют, потом соединяют. Подзапрос делает это «внутри строки», CTE — именованными шагами. Здесь собраны конструкции, их цена и ловушки — с живыми планами и выводом psql.

Самое главное
  • Подзапрос возвращает значение или набор строк «внутри» запроса; CTE даёт шагу имя через WITH и читается сверху вниз.
  • Для анти-соединения берите NOT EXISTS, а не NOT IN: NULL в подзапросе делает NOT IN пустым для всех строк.
  • В PostgreSQL 12+ CTE по умолчанию встраивается в запрос, а не материализуется. Нужен отдельный расчёт — AS MATERIALIZED.

01Что это и как устроено

Подзапрос — это SELECT внутри другого запроса. Он может вернуть одно значение для сравнения, список значений для IN или просто ответить «есть ли такая строка» для EXISTS. Коррелированный подзапрос ссылается на строку внешнего запроса и фактически выполняется для каждой такой строки.

CTE (WITH name AS (...)) — именованный шаг того же запроса: на результат можно ссылаться дальше как на таблицу. Это про читаемость и структуру, а не про автоматическое ускорение. Живёт CTE только внутри одного запроса; временная таблица — на всю сессию и требует DDL.

📝
Держите эту картинку в голове

Разложить вопрос на шаги. Подзапрос — пометка на полях: работает, но если пометок много, читать тяжело. CTE — черновик с заголовком: шаг вынесли, назвали (WITH order_revenue AS (...)) и дальше ссылаетесь на него как на таблицу.

Логика ответа та же, но видно, из каких частей он собран. Подробный разбор — в главе 22.

03Синтаксис-шаблон

Минимальный скелет CTE: шаг объявляется до основного запроса и получает имя. Скалярный подзапрос выглядит как обычное сравнение с (SELECT ...) — он разобран в разделе 05.

CTE: именованный шаг

ref_sql_cte_lab.sqlsql
WITH user_totals AS (
    SELECT user_id, SUM(quantity * price) AS total
    FROM orders o JOIN products p ON p.id = o.product_id
    GROUP BY user_id
)
SELECT u.name, t.total
FROM user_totals t JOIN users u ON u.id = t.user_id
ORDER BY t.total DESC, u.name;
name | total -------+---------- Anna | 76950.00 Olga | 76500.00 Ivan | 23800.00 Petr | 22000.00 Maria | 2250.00 (5 rows)

Шаблон читается так: WITH user_totals AS (...) — «сначала посчитай итоги по пользователям», затем основной SELECT соединяет их с users. Имя живёт до конца запроса; вложенные запросы могут ссылаться только на объявленные выше.

05Разбор по вариантам

Все примеры — в файле ref_sql_cte_lab.sql. Вывод — реальный psql на базе learning_shop.

Скалярный подзапрос в WHERE

ref_sql_cte_lab.sqlsql
SELECT o.id, (o.quantity * p.price) AS revenue
FROM orders o JOIN products p ON p.id = o.product_id
WHERE (o.quantity * p.price) > (
    SELECT AVG(quantity * price) FROM orders o2
    JOIN products p2 ON p2.id = o2.product_id
)
ORDER BY revenue DESC, o.id;
id | revenue ----+---------- 1 | 75000.00 9 | 75000.00 5 | 22000.00 10 | 22000.00 (4 rows)

Внутренний запрос выполняется один раз, его результат подставляется в сравнение. Заказы с выручкой ровно 20240.00 не попали: условие строгое.

IN и ANY

ref_sql_cte_lab.sqlsql
SELECT id, name FROM users
WHERE id IN (SELECT user_id FROM orders WHERE quantity >= 3)
ORDER BY id;

SELECT id, name FROM users
WHERE id = ANY (ARRAY[1, 3])
ORDER BY id;
id | name ----+------- 1 | Anna 5 | Maria (2 rows) id | name ----+------ 1 | Anna 3 | Olga (2 rows)

IN сравнивает с каждым значением подзапроса; ANY делает то же для массива. Список из подзапроса может содержать NULL — для IN это не опасно, для NOT IN опасно (раздел 07).

EXISTS и NOT EXISTS

ref_sql_cte_lab.sqlsql
SELECT u.id, u.name
FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id)
ORDER BY u.id;

SELECT o.id, o.created_at
FROM orders o
WHERE NOT EXISTS (SELECT 1 FROM users u WHERE u.id = o.user_id);
id | name ----+------- 1 | Anna 2 | Ivan 3 | Olga 4 | Petr 5 | Maria (5 rows) id | created_at ----+--------------------- 8 | 2024-03-07 19:30:00 (1 row)

EXISTS останавливается на первой найденной строке — значение внутри SELECT не вычисляется. NOT EXISTS — каноническое анти-соединение: заказ id = 8 остался без пользователя.

Коррелированный подзапрос

ref_sql_cte_lab.sqlsql
SELECT u.name,
       (SELECT COUNT(*) FROM orders o WHERE o.user_id = u.id) AS orders
FROM users u
ORDER BY u.id;
name | orders -------+-------- Anna | 3 Ivan | 2 Olga | 2 Petr | 1 Maria | 1 (5 rows)

Подзапрос ссылается на u.id снаружи, поэтому выполняется для каждого пользователя. На пяти строках это незаметно; на 100 000 — уже 100 000 подзапросов. Обычная замена — LEFT JOIN ... GROUP BY.

Несколько CTE: агрегат, потом фильтр

ref_sql_cte_lab.sqlsql
WITH order_revenue AS (
    SELECT o.id, o.user_id, o.quantity * p.price AS revenue
    FROM orders o JOIN products p ON p.id = o.product_id
),
user_totals AS (
    SELECT user_id, SUM(revenue) AS total
    FROM order_revenue
    GROUP BY user_id
),
big_spenders AS (
    SELECT user_id, total FROM user_totals WHERE total > 50000
)
SELECT u.name, b.total
FROM big_spenders b JOIN users u ON u.id = b.user_id
ORDER BY b.total DESC, u.name;
name | total ------+---------- Anna | 76950.00 Olga | 76500.00 (2 rows)

Шаги выстраиваются цепочкой: order_revenue → user_totals → big_spenders. Фильтр total > 50000 стоит уже после агрегата, а не до него. Каждый следующий шаг видит только предыдущие, поэтому порядок объявления — часть логики.

Рекурсивный CTE: числа

ref_sql_cte_lab.sqlsql
WITH RECURSIVE numbers AS (
    SELECT 1 AS n
    UNION ALL
    SELECT n + 1 FROM numbers WHERE n < 5
)
SELECT n FROM numbers;
n --- 1 2 3 4 5 (5 rows)

Три части: старт (SELECT 1), соединение (UNION ALL) и рекурсивный шаг с условием WHERE n < 5. Условие — единственное, что останавливает последовательность; без него запрос не завершится.

06Три сценария на learning_shop

Отчёт: выше средней выручки

ref_sql_cte_lab.sqlsql
WITH order_revenue AS (
    SELECT o.id, o.user_id, o.quantity * p.price AS revenue
    FROM orders o JOIN products p ON p.id = o.product_id
),
user_totals AS (
    SELECT user_id, SUM(revenue) AS total
    FROM order_revenue
    GROUP BY user_id
)
SELECT u.name, t.total
FROM user_totals t JOIN users u ON u.id = t.user_id
WHERE t.total > (SELECT AVG(total) FROM user_totals)
ORDER BY t.total DESC, u.name;
name | total ------+---------- Anna | 76950.00 Olga | 76500.00 (2 rows)

Вопрос звучит как «кто выше среднего», но среднее считается по готовым суммам, а не по заказам. Поэтому сначала два CTE, потом подзапрос со средним. Порядок шагов здесь — и есть решение задачи.

Пользователи, не покупавшие в феврале

ref_sql_cte_lab.sqlsql
SELECT u.id, u.name
FROM users u
WHERE NOT EXISTS (
    SELECT 1 FROM orders o
    WHERE o.user_id = u.id
      AND o.created_at >= '2024-02-01'
      AND o.created_at < '2024-03-01'
)
ORDER BY u.id;
id | name ----+------ 1 | Anna 4 | Petr (2 rows)

Анти-соединение с дополнительным условием по датам: «нет строки за февраль». В этой базе заказы есть у всех пяти пользователей, поэтому вопрос «совсем без заказов» вернул бы пустой результат — а с периодом он осмыслен. Пустой ответ здесь корректен, а не ошибка.

Рекурсивный календарь месяцев

ref_sql_cte_lab.sqlsql
WITH RECURSIVE months AS (
    SELECT DATE '2024-01-01' AS month
    UNION ALL
    SELECT (month + INTERVAL '1 month')::date FROM months
    WHERE month < DATE '2024-06-01'
),
monthly AS (
    SELECT DATE_TRUNC('month', o.created_at)::date AS month,
           SUM(o.quantity * p.price) AS revenue
    FROM orders o JOIN products p ON p.id = o.product_id
    GROUP BY 1
)
SELECT m.month, COALESCE(mo.revenue, 0) AS revenue
FROM months m LEFT JOIN monthly mo ON mo.month = m.month
ORDER BY m.month;
month | revenue ------------+---------- 2024-01-01 | 78150.00 2024-02-01 | 25750.00 2024-03-01 | 98500.00 2024-04-01 | 0 2024-05-01 | 0 2024-06-01 | 0 (6 rows)

Рекурсия строит полный ряд месяцев, а LEFT JOIN оставляет месяцы без продаж с нулём через COALESCE. Так делают отчёты, где «нет данных» должно быть явной строкой, а не пропуском.

07Пять ошибок, на которых спотыкаются

NOT IN с NULL

Если в подзапросе (или списке) есть NULL, NOT IN даёт unknown для каждой строки — и вы получаете пустой результат там, где ждали три строки. Проверено: id NOT IN (2, 4, NULL) возвращает 0 строк, хотя Anna, Olga и Maria подходят.

Для анти-соединения — NOT EXISTS. Для NOT IN — отфильтровать NULL: WHERE user_id IS NOT NULL.
Коррелированный подзапрос в цикле

Подзапрос, который ссылается на внешнюю строку, выполняется для каждой строки внешнего запроса. На маленькой таблице это незаметно, на orders_big — сто тысяч обращений к users.

Переписать в JOIN + GROUP BY или оконную функцию: один проход вместо n подзапросов.
Рекурсия без условия остановки

WITH RECURSIVE без WHERE в рекурсивной части не завершится: каждая итерация снова порождает строку. LIMIT снаружи не спасает — рекурсия вычисляется до применения лимита.

Условие в рекурсивной части обязательно: WHERE n < 5, WHERE month < DATE '2024-06-01'. Плюс проверка на NULL.
Верить, что CTE всегда материализуется

В PostgreSQL 12+ обычный WITH встраивается в основной запрос: в плане Subquery Scan, а не CTE Scan. Ждать от него «кэша» или отдельного расчёта не стоит.

Нужен отдельный расчёт — AS MATERIALIZED. Нужно встроить обратно — AS NOT MATERIALIZED.
Одинаковые имена шагов и колонок

Два CTE с одним именем — ошибка; одинаковые колонки в шагах и таблицах дают неоднозначность при соединении. SELECT total в запросе с двумя источниками total не выполнится.

Уникальные имена шагов и явные списки колонок: WITH user_totals(user_id, total) AS (...), а к колонкам — t.total.

08Мини-проверка

Пять вопросов на понимание и две задачи. Сначала своя попытка — потом спойлер.

Чем CTE отличается от подзапроса?

Синтаксически — именем и местом: CTE объявляется до основного запроса (WITH name AS (...)) и на него ссылаются как на таблицу. Подзапрос живёт внутри выражения. По смыслу оба — шаги одного запроса; в PG 12+ CTE по умолчанию встраивается так же, как подзапрос.

Резюме: CTE — это подзапрос, которому дали имя и вынесли наверх.
Когда IN, а когда EXISTS?

IN — когда подзапрос возвращает список значений и вы сравниваете с ним. EXISTS — когда важен сам факт существования строки. Для анти-соединения NOT EXISTS безопаснее: NOT IN ломается о NULL.

Резюме: IN — про значения, EXISTS — про факт.
Почему коррелированный подзапрос дорогой и что вместо него?

Он зависит от строки внешнего запроса и выполняется для каждой строки — n строк дают n запусков внутреннего запроса. Замена: JOIN + GROUP BY или оконная функция — один проход по данным.

Резюме: коррелированный — «спросить заново для каждой строки».
Как остановить рекурсивный CTE?

Условием в рекурсивной части: WHERE month < DATE '2024-06-01' или WHERE n < 5. Базовый шаг даёт первую строку, рекурсивный — следующую, пока условие истинно. LIMIT снаружи не является условием остановки.

Резюме: без WHERE в рекурсивной части запрос не завершится.
Материализуется ли CTE в PostgreSQL 14?

По умолчанию нет: он встраивается в план (Subquery Scan). AS MATERIALIZED заставляет посчитать шаг один раз (CTE Scan). Это инструмент под задачу, а не «всегда быстрее».

Резюме: обычный WITH — встроенный; MATERIALIZED — отдельный расчёт.

01 Пользователи с числом заказов меньше двух

Сколько заказов у каждого пользователя и кто заказал меньше двух раз? Учтите и тех, у кого заказов нет.

условиеsql
-- ожидается: Petr и Maria — по одному заказу
Показать решение и разбор
решениеsql
WITH user_orders AS (
    SELECT u.id, u.name, COUNT(o.id) AS orders
    FROM users u LEFT JOIN orders o ON o.user_id = u.id
    GROUP BY u.id, u.name
)
SELECT name, orders
FROM user_orders
WHERE orders < 2
ORDER BY id;
name | orders -------+-------- Petr | 1 Maria | 1 (2 rows)

Что важно. LEFT JOIN сохраняет пользователей без заказов, COUNT(o.id) считает только реальные заказы и даёт 0. Фильтр по агрегату стоит в финальном WHERE — именно для этого и нужен второй шаг.

02 Категории выше средней выручки

Посчитайте выручку по категориям и оставьте те, что выше средней по категориям.

условиеsql
-- ожидается: electronics — единственная категория выше средней
Показать решение и разбор
решениеsql
WITH category_revenue AS (
    SELECT p.category, SUM(o.quantity * p.price) AS revenue
    FROM orders o JOIN products p ON p.id = o.product_id
    GROUP BY p.category
)
SELECT category, revenue
FROM category_revenue
WHERE revenue > (SELECT AVG(revenue) FROM category_revenue)
ORDER BY revenue DESC;
category | revenue -------------+----------- electronics | 195500.00 (1 row)

Что важно. Среднее по категориям — это среднее от готовых сумм, поэтому подзапрос ссылается на тот же CTE category_revenue. Считать среднее по всем заказам было бы другой задачей.

09Мостик: та же идея в pandas и Python

pandas: промежуточные переменные вместо CTE

мост в pandaspython
merged = orders.merge(products, left_on="product_id", right_on="id")
merged["revenue"] = merged["quantity"] * merged["price"]        # order_revenue

order_revenue = merged[["id", "user_id", "revenue"]]             # первый шаг
user_totals = order_revenue.groupby("user_id", as_index=False)["revenue"].sum()

report = user_totals.merge(users, on="user_id")                 # финальный SELECT
report.where(report["revenue"] > report["revenue"].mean()).dropna()

В pandas аналог CTE — обычная промежуточная переменная: результат шага присвоили имени и используют дальше. Подзапрос IN похож на isin, EXISTS — на проверку notna/наличие ключа. Рекурсивного CTE в pandas нет — календарь строят через pd.date_range, иерархию — циклом. В чистом Python ту же роль играет set: id in user_ids — это EXISTS, а not in — NOT EXISTS.
