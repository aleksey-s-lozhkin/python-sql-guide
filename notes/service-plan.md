# Сервис: архитектура и план

Книга готова (26 глав + 4 проверочные). Дальше — слой практики: аккаунты, синхронизация
прогресса и проверка SQL-задач на реальной базе. Ниже — как это устроить, не ломая то, что уже
работает.

## Главное решение: не уходим от PWA, а добавляем слой практики

Книга и сервис — разные слои с разной ценой поддержки:

| Слой | Где живёт | Зачем |
|---|---|---|
| Контент (26 глав, проверочные) | `guide/`, GitHub Pages, PWA | читать офлайн, без аккаунта, бесплатно |
| Практика (аккаунты, прогресс, SQL-проверка) | `app/`, FastAPI + PostgreSQL | проверять себя на живой базе |

Если «уйти от репозитория и PWA» — значит потерять офлайн-чтение и бесплатный хостинг.
Правильнее: PWA остаётся учебником, сервис добавляет кнопку «Практика» и синхронизацию.
Без входа книга работает как сейчас; прогресс хранится локально и синкается при входе.

## Схема

```
GitHub Pages (static)          VPS / Docker
┌────────────────────┐        ┌─────────────────────────────┐
│ guide/             │  ссылки│  Caddy (TLS)                │
│ 26 глав + задания  │───────▶│   ├── /            → app UI │
│ PWA, офлайн        │        │   └── /api         → FastAPI│
└────────────────────┘        │        ├── auth            │
                              │        ├── progress        │
                              │        └── sql_runner      │
                              │  PostgreSQL                 │
                              │   ├── app (users, progress) │
                              │   └── learning_shop         │
                              │       (read-only роль)      │
                              └─────────────────────────────┘
```

## Что в репозитории

```
guide/                     — как сейчас, без изменений в содержании
app/
  api/
    main.py                — FastAPI, роуты
    auth.py                — регистрация, вход, сессии
    progress.py            — прогресс и синхронизация
    tasks.py               — список задач, проверка
    sql_runner.py          — безопасное выполнение SQL
    db.py, models.py       — SQLAlchemy/psycopg
  data/tasks/*.yaml        — задачи: условие, эталонный SQL, правила сравнения
  web/                     — страницы практики (в стиле книги, без фреймворка)
  migrations/*.sql
deploy/
  docker-compose.yml       — postgres + api + caddy
  Caddyfile
  backup.sh                — pg_dump по cron
```

## Модель данных (`app` schema)

- `users(id, email, password_hash, created_at)`
- `sessions(id, user_id, token_hash, expires_at)`
- `progress(user_id, chapter_slug, status, updated_at)` — PK (user_id, chapter_slug)
- `submissions(id, user_id, task_slug, sql_text, ok, error, ms, created_at)`
- `tasks` — либо YAML в репо, либо таблица; на старте YAML проще ревьюить.

Книга остаётся источником истины по контенту; сервис знает только slug и статус.

## Проверка SQL: как безопасно

1. Отдельная база/схема `learning_shop` и роль `learner_ro` с правом только `SELECT`.
2. Каждое выполнение: `SET TRANSACTION READ ONLY`, `SET statement_timeout = '3s'`,
   `SET idle_in_transaction_session_timeout`, лимит строк (обёртка `SELECT * FROM (...) LIMIT 1001`).
3. Разрешаем один запрос, начинающийся с `SELECT`/`WITH`; парсим `sqlparse`, отсекаем `;`-цепочки.
4. Сравнение с эталоном по результату, а не по тексту: колонки, типы, строки; порядок учитываем
   только для задач с `ordered: true`. Числа сравниваем с допуском (NUMERIC vs float).
5. Ошибки возвращаем человеческим текстом: «нет такой колонки», «лишние строки: 2», «не совпало
   значение revenue у Anna».
6. Рейт-лимит: не чаще 1 запроса в 2 секунды и N запросов в день на пользователя.
7. Никаких `COPY ... TO PROGRAM`, `pg_read_file`, суперпользователей; база сервиса — не продовая.

## Этапы

| Этап | Что | Оценка |
|---|---|---|
| 0 | каркас `app/`, docker-compose, миграции, `/health` | 0.5 дня |
| 1 | регистрация/вход, сессии, прогресс + синк | 1–2 дня |
| 2 | SQL-раннер, 8–10 задач из глав 19–24, UI проверки | 2–3 дня |
| 3 | интеграция с книгой: «Практика», синк прогресса | 1 день |
| 4 | деплой на VPS (Caddy), бэкапы, мониторинг | 0.5–1 день |

Основная сложность и риск — этап 2: безопасное исполнение чужого SQL и сравнение результатов.
Остальное — обычная веб-разработка.

## Хостинг: варианты

1. **VPS (рекомендую):** Hetzner CX22 / Timeweb ~400–600 ₽/мес, Docker Compose, Caddy с TLS,
   Postgres в том же compose с volume и ночным `pg_dump`. Полный контроль, дёшево.
2. **PaaS:** Render/Fly.io + Neon (Postgres free tier) — проще деплой, но SQL-раннер всё равно
   нужен в контейнере; холодные старты и лимиты.
3. **Только локально:** Docker Compose на ноутбуке — 0 ₽, отлично для разработки и личного
   использования; для публичного сервиса не подходит.

Домен (`app.<домен>`) — опционально; Pages остаётся `aleksey-s-lozhkin.github.io/python-sql-guide`.

## Что сознательно не делаем на старте

- Python-песочницу (нужен отдельный контейнер, docker-in-docker, риск побега) — отдельный этап.
- Очереди, соцфункции, оплату, мобильное приложение, leaderboard.
- Мультикурсы: один курс, один набор задач.

## Риски и как снижаем

- **Исполнение SQL:** read-only роль, таймауты, лимит строк, отдельная БД; тесты на «злые» запросы.
- **Обслуживание VPS:** автообновления, бэкапы, health-check; либо managed Postgres.
- **Офлайн книги:** синк best-effort, локальный прогресс — источник при офлайне.
- **Стоимость:** VPS + домен; при росте — managed Postgres.

## Ближайший шаг

Этап 0 + 1 локально: `docker compose up` поднимает Postgres с `learning_shop` и `app`-схемой,
FastAPI отдаёт `/health`, регистрацию и прогресс. Затем — первая задача с проверкой SQL
(«топ-3 пользователей по выручке»), чтобы увидеть весь путь на одном примере.
