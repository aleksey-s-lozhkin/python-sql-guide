# Песочница для практики: варианты и рекомендация

Вопрос: как дать ученику «настоящую» песочницу — SQL с DDL/DML, Python/pandas, может быть
интерактив — не превращая сервис в дырявый хостинг чужого кода.

## Что считается «функциональной» песочницей

1. **SQL-практика:** не только SELECT, но и CREATE/INSERT/UPDATE/DELETE в своей схеме,
   ошибки, EXPLAIN, транзакции; сброс к исходному состоянию.
2. **Python/pandas:** запуск кода с numpy/pandas, чтение учебных CSV, тесты; вывод и ошибки.
3. **Интерактив (опционально):** REPL/Jupyter-подобная сессия, где можно экспериментировать
   между проверками.

## Модель угроз

| Угроза | Пример | Что нужно |
|---|---|---|
| Побег из песочницы | доступ к файлам хоста, docker socket | namespaces, seccomp, rootless, отдельная ВМ |
| Сеть | сканирование, атаки, майнинг | `--network=none`, egress-фильтр |
| Ресурсы | fork bomb, память, CPU, диск | cgroups: pids, memory, cpu, tmpfs |
| Данные | чтение `app.users`, чужих работ | отдельная БД/схема, отдельный кластер |
| DoS базы | тяжёлый запрос, много соединений | statement_timeout, work_mem, лимит соединений |
| Злоупотребление | сотни запусков, спам | квоты, очередь, TTL, рейт-лимит |

## Уровни изоляции

| Вариант | Изоляция | Старт | Сложность | Когда выбирать |
|---|---|---|---|---|
| Отдельная роль/схема в PostgreSQL | логическая, общий процесс | мс | низкая | SQL без Python, DDL в своей схеме |
| Docker-контейнер на запуск | namespaces + cgroups | 0.5–2 с | средняя | Python/pandas, стандарт индустрии |
| Docker + gVisor (`runsc`) | свой kernel-интерфейс | 1–3 с | средне-высокая | публичный сервис, недоверенный код |
| Firecracker microVM | KVM, отдельное ядро | ~125 мс | высокая | много арендаторов, жёсткая изоляция |
| nsjail / isolate | namespaces, лёгкий | 10–100 мс | средняя | олимпиадные судьи на C++ |
| Отдельная ВМ на пользователя | полная | 10–60 с | высокая | долгие лаборатории, не проверки |
| Wasm (Pyodide, DuckDB-WASM) | браузер | мс | низкая | офлайн-практика без сервера |
| Managed API (E2B, Modal, Judge0/Piston) | чужая инфраструктура | 1–10 с | низкая | быстро запустить, не обслуживать |

## «Свой контейнер на пользователя»: четыре модели

1. **На каждую проверку** — самый безопасный и простой в уборке: контейнер живёт 2–5 секунд.
   Холодный старт Docker — главная цена; лечится тёплым пулом (pre-warmed containers).
2. **На сессию** — контейнер живёт 10–30 минут, можно делать несколько запусков, ближе к REPL.
   Нужны TTL, лимиты, очистка, защита от «занял и не отпустил».
3. **На пользователя** — долгоживущий контейнер/ВМ, состояние сохраняется. Дорого по памяти,
   нужны квоты и автостоп по бездействию; скорее для «лаборатории», чем для задач.
4. **На арендатора (ВМ/пул)** — общая ВМ для раннера, контейнеры внутри. Практичный компромисс:
   веб и БД на одной ВМ, раннер — на другой, без доступа к внутренней сети.

**Рекомендация:** проверки — на каждую отправку (модель 1), интерактив — сессия (модель 2),
и всё это на отдельной ВМ раннера.

## SQL-песочница: дешевле, чем контейнеры

Для SQL обычно не нужен отдельный контейнер: достаточно отдельной схемы и роли.

```sql
-- при подключении пользователя
CREATE SCHEMA IF NOT EXISTS work AUTHORIZATION learner;
SET search_path = work, public;          -- public — только чтение справочников
SET statement_timeout = '2s';
SET lock_timeout = '1s';
SET work_mem = '32MB';
-- DDL разрешён только в work: роль не владеет public и app
```

- **Сброс:** `DROP SCHEMA work CASCADE; CREATE SCHEMA work;` + заново выдать права.
- **Изоляция от сервиса:** отдельная база/кластер, роль без доступа к `app`, без superuser,
  без `CREATEROLE`, без `COPY ... PROGRAM` (и так требует superuser).
- **Лимиты:** `statement_timeout`, `idle_in_transaction_session_timeout`, `max_connections`
  на роль через `ALTER ROLE ... CONNECTION LIMIT`, отдельный пул.
- **Проверка результата:** тот же сравненитель, что уже есть (`app/api/checker.py`).

Это покрывает 80% «хочу больше, чем SELECT» без контейнеров и почти без риска.

## Python-песочница: Docker-раннер

Отдельный сервис-воркер, который получает задание из очереди и запускает контейнер:

```bash
docker run --rm \
  --network=none \
  --read-only --tmpfs /tmp:size=64m,noexec \
  --memory=256m --memory-swap=256m \
  --cpus=0.5 --pids-limit=64 \
  --cap-drop=ALL --security-opt=no-new-privileges \
  --user=65534:65534 \
  --ulimit=nofile=64 \
  --label=job=<id> \
  guide-runner:py312 \
  python /task/run.py
```

Что ещё обязательно:

- **rootless Docker** или userns-remap; AppArmor/seccomp-профиль по умолчанию уже режет часть
  syscall'ов, но лучше свой.
- **таймаут** снаружи (`timeout 5s` + kill по label), лимит вывода (первые 64 КБ), лимит файлов.
- **образ только с нужным**: python + numpy + pandas, без компиляторов, без pip, без сети.
- **данные** монтируются read-only (`-v task:/task:ro`), запись только в tmpfs.
- **веб не имеет docker socket**: очередь (Redis/RQ, Postgres LISTEN/NOTIFY, файлы) между API
  и воркером; воркер — отдельный процесс/контейнер с доступом к Docker.
- **отдельная ВМ** раннера: если контейнер убежит, он не доберётся до БД и аккаунтов.
- **квоты**: N запусков в минуту, очередь, максимум одновременных контейнеров.

## Что делают онлайн-судьи

По публичным описаниям и открытым проектам (Judge0, Piston, DOMjudge, e-olymp) схема типовая:

- на каждую отправку — изолированный процесс/контейнер;
- нет сети, лимиты CPU/памяти/времени, запрет fork-бомб;
- проверка — по тестам/выводу (stdout, файлы, иногда эталонный вывод);
- SQL-задачи в учебных платформах обычно выполняются на отдельной БД и сравниваются
  **результаты запроса**, а не текст (как у нас уже сделано);
- «песочница» Stepik/Python Tutor — это тот же принцип: код исполняется вне основного
  приложения, результат возвращается как данные.

Отсюда вывод: не нужно изобретать «контейнер на пользователя» для проверок — нужен
**эфемерный запуск + сравнение результата**, а «контейнер на пользователя» оставить для
интерактивных сессий.

## Альтернатива без сервера: Wasm

- **Pyodide** (CPython в WebAssembly) + numpy/pandas — запуск в браузере, офлайн, без риска
  для сервера; минус: 10–20 МБ загрузки, часть пакетов недоступна, медленнее.
- **DuckDB-WASM / sql.js** — SQL в браузере, но не PostgreSQL-диалект.
- Подходит для «попробуй pandas» в книге; не подходит, если нужен ровно PostgreSQL.

## Managed-варианты, если не хочется обслуживать

- **E2B, Modal, Daytona, Fly Machines** — API «запусти код в микро-ВМ», оплата по времени.
- **Piston / Judge0** — self-hosted судьи, можно поднять в Docker и не писать раннер.
- **Cloudflare Sandbox / Workers** — для JS/Wasm-сценариев.

Плюс: быстро. Минус: зависимость от чужого API, данные уходят наружу, цена при росте.

## Рекомендуемый план для этого проекта

| Этап | Что | Оценка |
|---|---|---|
| P1 | SQL-песочница: схема `work` на пользователя, DDL/DML, сброс, лимиты | 1–2 дня |
| P2 | Python-раннер в Docker (numpy/pandas), 5–8 задач, очередь, лимиты | 3–5 дней |
| P3 | Отдельная ВМ раннера + rootless Docker / gVisor, квоты и мониторинг | 2–3 дня |
| P4 | Интерактивная сессия (Jupyter/REPL) с TTL — опционально | 3–5 дней |

P1 даёт максимум «функциональности за деньги» без контейнеров. P2 — то, что обычно и называют
песочницей. P3 — гигиена, если сервис публичный. P4 — уже отдельный продукт.

## Итог

- Для SQL — отдельная схема и роль, без контейнеров.
- Для Python — эфемерный Docker-контейнер на запуск, без сети, с лимитами, на отдельной ВМ.
- «Свой контейнер каждому пользователю навсегда» — дорого и не нужно; лучше сессия с TTL.
- Сильная изоляция (gVisor/Firecracker) — когда появится публичный трафик и чужие данные.
