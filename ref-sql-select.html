SELECT, WHERE и NULL Как выбрать строки, не споткнуться о пропуски и стабильно отсортировать результат

SELECT — способ задать таблице вопрос: какие строки, какие колонки, в каком порядке. Здесь — конвейер запроса, полный набор условий WHERE, логика трёх значений и точный вывод psql на базе learning_shop.

Самое главное
  • Запрос пишется сверху вниз, а выполняется по конвейеру: FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT. Поэтому алиас виден в ORDER BY, но не в WHERE.
  • NULL — отсутствие значения: = NULL и <> '…' пропуск не находят, нужен IS NULL. NULL внутри NOT IN обнуляет результат.
  • COUNT(*) считает строки, COUNT(col) — непустые значения. Без ORDER BY порядок не определён, а NULLS FIRST/LAST задаёт место пропусков явно.

01Что это и как читается

SELECT — декларация: вы описываете, что хотите получить, а не как это добывать. База сама решает, читать ли таблицу целиком, идти по индексу или строить хеш — на результат это не влияет, на скорость влияет сильно.

Читается запрос сверху вниз, но смысл задаёт конвейер этапов: сначала FROM строит множество строк, WHERE оставляет нужные, GROUP BY собирает группы, и только потом SELECT вычисляет колонки и алиасы. Дальше — DISTINCT, ORDER BY и LIMIT.

Порядок логический: физически база может делать иначе, но результат обязан ему соответствовать. Подробно — в главе 19.

🏭
Держите эту картинку в голове

Запрос — это сборочный конвейер. На ленту попадают детали (FROM), брак отбрасывается (WHERE), детали собираются в узлы (GROUP BY), узлы проверяются (HAVING), затем выбирается то, что нужно показать (SELECT), убираются дубли (DISTINCT), всё сортируется (ORDER BY) и только в конце отрезается нужное количество (LIMIT).

SELECT стоит в середине конвейера. Поэтому алиасы, придуманные в SELECT, не существуют на этапе WHERE — их ещё не создали. Метафору целиком разбирает глава 19.

03Синтаксис-шаблон

Минимальный рабочий запрос — список колонок, FROM, WHERE и LIMIT. Порядок ключевых слов фиксирован: ненужные этапы можно выбрасывать, менять их местами — нельзя.

ref_sql_select_lab.sqlsql
SELECT name, city, email
FROM users
WHERE city IS NOT NULL
ORDER BY name
LIMIT 3;
name | city | email -------+-----------------+-------------- Anna | Москва | anna@mail.ru Ivan | Казань | ivan@mail.ru Maria | Санкт-Петербург | (3 rows)

Вывод в книге — это stdout psql: заголовки, разделитель и строка (N rows). Пропуск печатается пустой ячейкой — так psql показывает NULL по умолчанию.

Псевдоним AS даёт колонке имя в результате. Оно появляется на этапе SELECT, поэтому ORDER BY его видит:

ref_sql_select_lab.sqlsql
SELECT name, price * 1.2 AS price_with_tax
FROM products
ORDER BY price_with_tax DESC, name
LIMIT 3;
name | price_with_tax ---------+---------------- Ноутбук | 90000.000 Монитор | 26400.000 Мышь | 1800.000 (3 rows)

А в WHERE тот же алиас — ошибка: WHERE выполняется раньше SELECT. Подробнее — ошибка №3.

05Разбор по вариантам

Все примеры страницы — в файле ref_sql_select_lab.sql: его можно запустить на learning_shop и сравнить вывод.

DISTINCT и NULL

ref_sql_select_lab.sqlsql
SELECT DISTINCT city
FROM users
ORDER BY city;
city ----------------- Казань Москва Санкт-Петербург (4 rows)

Четыре строки, а не три: NULL для DISTINCT — такое же отдельное значение, как «Москва». В psql его ячейка выглядит пустой.

WHERE: = NULL, IS NULL и <>

ref_sql_select_lab.sqlsql
SELECT id, name
FROM users
WHERE city = NULL;

SELECT id, name, city
FROM users
WHERE city IS NULL;

SELECT name, city
FROM users
WHERE city <> 'Москва'
ORDER BY name;
id | name ----+------ (0 rows) id | name | city ----+------+------ 4 | Petr | (1 row) name | city -------+----------------- Ivan | Казань Maria | Санкт-Петербург (2 rows)

= NULL не находит ничего: сравнение с неизвестным даёт UNKNOWN. IS NULL находит Petr. А <> 'Москва' не включает Petr: NULL <> 'Москва' — тоже UNKNOWN. Нужны «все, кроме Москвы, включая неизвестных» — OR city IS NULL.

IN и NOT IN с NULL

ref_sql_select_lab.sqlsql
SELECT name, city
FROM users
WHERE city IN ('Москва', 'Казань')
ORDER BY name;

SELECT name, city
FROM users
WHERE city IN ('Москва', NULL)
ORDER BY name;

SELECT name
FROM users
WHERE city NOT IN (SELECT city FROM users)
ORDER BY name;
name | city ------+-------- Anna | Москва Ivan | Казань Olga | Москва (3 rows) name | city ------+-------- Anna | Москва Olga | Москва (2 rows) name ------ (0 rows)

IN с обычным списком работает предсказуемо. Второй запрос кладёт NULL прямо в список: он не находит пропуск и не ломает остальные совпадения — просто «не совпадает ни с чем». А NOT IN по подзапросу, в котором есть NULL, возвращает пусто: одно из сравнений даёт UNKNOWN, и итог не TRUE. Поэтому «не входит» пишут через NOT EXISTS — это приём страницы 05.

BETWEEN и LIKE/ILIKE

ref_sql_select_lab.sqlsql
SELECT name, price
FROM products
WHERE price BETWEEN 1000 AND 30000
ORDER BY price;

SELECT name
FROM users
WHERE city LIKE '%москва%'
ORDER BY name;

SELECT name
FROM users
WHERE city ILIKE '%москва%'
ORDER BY name;
name | price ---------+---------- Мышь | 1500.00 Монитор | 22000.00 (2 rows) name ------ (0 rows) name ------ Anna Olga (2 rows)

BETWEEN 1000 AND 30000 включает обе границы: «Мышь» (1500) и «Монитор» (22000) попали. LIKE в PostgreSQL учитывает регистр, поэтому «%москва%» ничего не находит; ILIKE — находит Anna и Olga.

ORDER BY, NULLS и LIMIT

ref_sql_select_lab.sqlsql
SELECT name, city
FROM users
ORDER BY city ASC NULLS FIRST, name;

SELECT name, city
FROM users
ORDER BY city DESC NULLS LAST, name
LIMIT 3;
name | city -------+----------------- Petr | Ivan | Казань Anna | Москва Olga | Москва Maria | Санкт-Петербург (5 rows) name | city -------+----------------- Maria | Санкт-Петербург Anna | Москва Olga | Москва (3 rows)

NULLS FIRST ставит Petr в начало, NULLS LAST — в конец. Второй ключ name нужен как тай-брейкер: у Anna и Olga одинаковый город, и без него порядок между ними не определён.

CASE, COALESCE и COUNT

ref_sql_select_lab.sqlsql
SELECT name,
       COALESCE(city, 'неизвестно') AS city_filled,
       CASE WHEN city IS NULL THEN 'нет данных' ELSE city END AS city_case
FROM users
ORDER BY id;

SELECT COUNT(*) AS all_rows,
       COUNT(city) AS known_city,
       COUNT(email) AS known_email
FROM users;
name | city_filled | city_case -------+-----------------+----------------- Anna | Москва | Москва Ivan | Казань | Казань Olga | Москва | Москва Petr | неизвестно | нет данных Maria | Санкт-Петербург | Санкт-Петербург (5 rows) all_rows | known_city | known_email ----------+------------+------------- 5 | 4 | 4 (1 row)

COALESCE подставляет запасное значение, CASE позволяет выразить любое правило. COUNT(*) вернул 5, COUNT(city) и COUNT(email) — по 4: у Petr нет города, у Maria нет email.

06Три сценария на learning_shop

Фильтр по городу с пропусками

ref_sql_select_lab.sqlsql
SELECT name, city
FROM users
WHERE city <> 'Москва' OR city IS NULL
ORDER BY name;
name | city -------+----------------- Ivan | Казань Maria | Санкт-Петербург Petr | (3 rows)

Типичная задача отчёта: «все, кроме Москвы». Без OR city IS NULL Petr выпал бы — его город неизвестен, а не «не Москва». Решение нужно принимать осознанно: иногда пропуски надо исключать, иногда показывать отдельной строкой.

Поиск по названию

ref_sql_select_lab.sqlsql
SELECT name, category, price
FROM products
WHERE name ILIKE '%о%'
ORDER BY price DESC;
name | category | price ---------+-------------+---------- Ноутбук | electronics | 75000.00 Монитор | electronics | 22000.00 Кофе | food | 450.00 (3 rows)

ILIKE '%о%' ищет подстроку без учёта регистра; сортировка по цене сразу превращает поиск в «самые дорогие из найденных». Для настоящего полнотекстового поиска в PostgreSQL есть tsvector, но для «найти в названии» хватает LIKE.

Топ-N с сортировкой

ref_sql_select_lab.sqlsql
SELECT id, name, price
FROM products
ORDER BY price DESC, name
LIMIT 3;
id | name | price ----+---------+---------- 1 | Ноутбук | 75000.00 5 | Монитор | 22000.00 2 | Мышь | 1500.00 (3 rows)

«Топ-3» — это всегда ORDER BY + LIMIT; один LIMIT без сортировки отдаёт произвольные строки. Второй ключ name делает результат воспроизводимым при равных ценах.

07Пять ошибок, на которых спотыкаются

= NULL вместо IS NULL

WHERE city = NULL не возвращает ничего: сравнение с неизвестным даёт UNKNOWN, а WHERE пропускает только TRUE. Тот же провал — с <> NULL.

IS NULL / IS NOT NULL.
NOT IN с NULL в подзапросе

WHERE city NOT IN (SELECT city FROM users) возвращает пусто, если в подзапросе есть NULL: одно сравнение даёт UNKNOWN и «отравляет» всю цепочку.

Фильтр WHERE city IS NOT NULL в подзапросе или NOT EXISTS (страница 05).
Алиас в WHERE

WHERE price_with_tax > 1000 после SELECT price * 1.2 AS price_with_tax падает: алиас создаётся на этапе SELECT, который идёт позже WHERE.

Повторить выражение, обернуть в подзапрос или CTE; для агрегатов — HAVING.
LIMIT без ORDER BY

Строки вернутся в том порядке, в котором их отдал план. Сегодня это «первые по вставке», завтра — другой план, и результат изменится.

Всегда ORDER BY; при равных значениях — второй ключ (например, id).
COUNT(*) как COUNT(col)

Числа расходятся при пропусках: в users это 5 против 4. Причина — COUNT(col) не считает NULL.

Решить, что нужно: строки (COUNT(*)) или известные значения (COUNT(col)).

08Мини-проверка

Пять вопросов и две задачи. Сначала своя попытка — потом спойлер.

В каком порядке логически выполняется запрос?

FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT. Текст пишется в другом порядке, но смысл задаёт конвейер.

Резюме: конвейер, а не текст.
Почему city = NULL не находит пропуски?

NULL — не значение, а его отсутствие. Любое сравнение с NULL даёт UNKNOWN, а WHERE пропускает только TRUE. Поэтому пропуск ищут проверкой факта: IS NULL.

Резюме: неизвестное нельзя сравнить — можно только проверить.
Почему алиас виден в ORDER BY, но не в WHERE?

Алиас создаётся на этапе SELECT. WHERE выполняется раньше, ORDER BY — позже. Это не прихоть синтаксиса, а следствие конвейера.

Резюме: всё решает позиция этапа.
Чем DISTINCT отличается от GROUP BY?

DISTINCT убирает повторы уже выбранных строк. GROUP BY собирает строки в группы, по которым можно считать агрегаты. Для «просто уникальных значений» достаточно DISTINCT, для «сколько и сколько в сумме» — GROUP BY.

Резюме: дедупликация результата против группировки для агрегатов.
Чем COUNT(*) отличается от COUNT(col)?

COUNT(*) считает строки, COUNT(col) — только непустые значения колонки. Разница равна числу NULL.

Резюме: строки против известных значений.

01 Пользователь без города

Выведите имя и email пользователей, у которых не указан город.

условиеsql
-- users(id, name, city, email); у Petr city IS NULL
Показать решение и разбор
решениеsql
SELECT name, email
FROM users
WHERE city IS NULL
ORDER BY name;
name | email ------+-------------- Petr | petr@mail.ru (1 row)

Что важно. = NULL здесь вернул бы 0 строк: пропуск находится только через IS NULL.

02 Три последних заказа

Выведите три заказа с самой поздней датой: id, дату и количество. Порядок должен быть воспроизводимым.

условиеsql
-- orders(id, user_id, product_id, quantity, created_at)
Показать решение и разбор
решениеsql
SELECT id, created_at, quantity
FROM orders
ORDER BY created_at DESC, id
LIMIT 3;
id | created_at | quantity ----+---------------------+---------- 10 | 2024-03-20 15:55:00 | 1 9 | 2024-03-15 13:10:00 | 1 8 | 2024-03-07 19:30:00 | 1 (3 rows)

Что важно. ORDER BY … DESC задаёт направление, id — тай-брейкер для одинаковых дат, LIMIT 3 отрезает результат уже после сортировки.

09Мостик: та же логика в pandas

pandas: те же условия, но маской

мост в pandaspython
import pandas as pd

users = pd.DataFrame({
    "name": ["Anna", "Ivan", "Olga", "Petr", "Maria"],
    "city": ["Москва", "Казань", "Москва", None, "Санкт-Петербург"],
    "email": ["anna@mail.ru", "ivan@mail.ru", "olga@mail.ru", "petr@mail.ru", None],
})

users[users["city"] == "Москва"]            # WHERE city = 'Москва'
users[users["city"].isna()]                 # WHERE city IS NULL
users[users["city"] != "Москва"]            # <> не включает NULL — так же, как в SQL
users["city"].isin(["Москва", "Казань"])    # WHERE city IN (...)
users["city"].drop_duplicates()             # SELECT DISTINCT city
users.sort_values("name").head(3)           # ORDER BY + LIMIT

==, isna, isin, drop_duplicates и sort_values — прямые аналоги SQL-конструкций. Разница в деталях: pandas умеет хранить пропуски разных типов (глава 17), а SQL знает один NULL.
