Индексы и EXPLAIN: оглавление книги Seq Scan, Index Scan, селективность и планы на PostgreSQL 14

Индекс — отдельная структура «ключ → строка», как оглавление у книги. Когда запрос тормозит, смотрят EXPLAIN: что планировщик выбрал и почему. Здесь — типы сканов, селективность, составные и covering-индексы, ошибки на реальных планах orders_big.

Самое главное
  • Индекс — отсортированная структура «ключ → ссылка на строку». Он ускоряет поиск и порядок, но занимает память и замедляет запись.
  • Планировщик выбирает Seq Scan или Index Scan по селективности и статистике: маленькая доля строк — индекс, большая — чтение всей таблицы.
  • Функция или приведение типа на колонке (created_at::date, id::text) выключают обычный индекс — условие перестаёт быть «по колонке».

Планы ниже сняты на этой базе командой EXPLAIN без ANALYZE — поэтому в них нет времени, только оценка cost и rows. Числа зависят от статистики и железа: на другой машине cost будет другим, а выбранный тип скана — как правило тем же.

01Что это и как устроено

Индекс в PostgreSQL — отдельная структура, в которой хранятся значения колонки и ссылки на строки таблицы. По умолчанию это btree: отсортированное дерево, где поиск по ключу — O(log n), а ещё есть диапазоны и порядок. Индекс не заменяет таблицу: найдя ссылку, база всё равно читает строку из heap.

Планировщик сравнивает цену вариантов по статистике. Seq Scan — прочитать всю таблицу подряд; Index Scan — идти по индексу и прыгать к строкам; Bitmap Heap Scan — собрать страницы с подходящими строками и прочитать их пачкой. Если строк много, чтение подряд оказывается дешевле — и индекс «не используется» вовсе не потому, что сломан.

📖
Держите эту картинку в голове

Индекс — оглавление книги. Без него, чтобы найти главу, приходится листать весь том (Seq Scan). С ним вы идёте по оглавлению к нужной странице (Index Scan) — быстро, но только если ищете по тому, что в оглавлении есть.

Не всякой книге нужно оглавление, и не всякому запросу — индекс. Планировщик решает по статистике: иногда пролистать десять страниц быстрее, чем открывать оглавление. Подробный разбор — в главе 24.

03Синтаксис-шаблон

План запрашивают командой EXPLAIN. Она не выполняет запрос: возвращает дерево узлов с оценкой стоимости. Вот точечный поиск по первичному ключу:

ref_sql_index_lab.sqlsql
EXPLAIN SELECT * FROM orders_big WHERE id = 4242;
QUERY PLAN ----------------------------------------------------------------------------------- Index Scan using orders_big_pkey on orders_big (cost=0.29..8.31 rows=1 width=24) Index Cond: (id = 4242) (2 rows)

Читается снизу вверх: Index Scan using orders_big_pkey — выбран индекс, Index Cond: (id = 4242) — по какому условию. А сам индекс в базе выглядит так (выполнять не нужно, это шаблон):

шаблон DDLsql
CREATE INDEX idx_orders_big_user ON orders_big (user_id);

-- covering: все нужные колонки внутри индекса
CREATE INDEX idx_orders_big_user_created
    ON orders_big (user_id) INCLUDE (created_at);

-- индекс по выражению — для условий вида created_at::date
CREATE INDEX idx_orders_big_day ON orders_big ((created_at::date));

В лаборатории эти команды не выполняются: только SELECT и EXPLAIN. Синтаксис DDL приведён для справки.

05Разбор по вариантам

Все примеры — в файле ref_sql_index_lab.sql. База learning_shop, таблица orders_big — 100 000 строк, по 20 000 на каждого из пяти пользователей.

Перед запуском

Нужна таблица orders_big (100 000 строк). Если её нет: psql -d learning_shop -f guide/snippets/ref_sql_setup.sql — скрипт создаст таблицу и зафиксирует статистику; базовая схема создаётся bash tools/setup_db.sh.

Seq Scan: подходящего индекса нет

ref_sql_index_lab.sqlsql
EXPLAIN SELECT * FROM orders_big WHERE quantity = 2;
QUERY PLAN ------------------------------------------------------------------ Seq Scan on orders_big (cost=0.00..1887.00 rows=33334 width=24) Filter: (quantity = 2) (2 rows)

По quantity индекса нет, и фильтр пропускает примерно треть строк — читать всё подряд дешевле. rows=33157 — это оценка планировщика, а не факт: фактические числа показывает EXPLAIN ANALYZE.

Index Scan: узкий диапазон дат

ref_sql_index_lab.sqlsql
EXPLAIN SELECT * FROM orders_big
WHERE created_at >= '2024-01-02' AND created_at < '2024-01-03';
QUERY PLAN ---------------------------------------------------------------------------------------------------------------------------------------------------------- Index Scan using idx_orders_big_created on orders_big (cost=0.29..58.09 rows=1440 width=24) Index Cond: ((created_at >= '2024-01-02 00:00:00'::timestamp without time zone) AND (created_at < '2024-01-03 00:00:00'::timestamp without time zone)) (2 rows)

Диапазон в сутки — около 1,5% строк. Индекс даёт и условие (Index Cond), и дешёвый порядок: cost 62 против 2137 у Seq Scan. Именно так выглядит «селективный фильтр».

Bitmap Heap Scan: 20% строк

ref_sql_index_lab.sqlsql
EXPLAIN SELECT * FROM orders_big
WHERE user_id = 3 AND quantity = 2;
QUERY PLAN ---------------------------------------------------------------------------------------- Bitmap Heap Scan on orders_big (cost=223.96..1160.96 rows=6667 width=24) Recheck Cond: (user_id = 3) Filter: (quantity = 2) -> Bitmap Index Scan on idx_orders_big_user (cost=0.00..222.29 rows=20000 width=0) Index Cond: (user_id = 3) (5 rows)

Один пользователь — это 20% таблицы. Индекс на user_id используется, но не для точечных прыжков: база собирает битмап страниц и читает их пачкой. Условие по quantity индекса не имеет и проверяется фильтром после чтения — Filter в плане. Составной индекс (user_id, quantity) позволил бы проверить оба условия по индексу; порядок колонок важен — первым идёт то, по чему фильтруют чаще.

Index Only Scan: индекс покрывает запрос

ref_sql_index_lab.sqlsql
EXPLAIN SELECT user_id FROM orders_big WHERE user_id = 3;
QUERY PLAN ------------------------------------------------------------------------------------------------- Index Only Scan using idx_orders_big_user on orders_big (cost=0.29..422.29 rows=20000 width=4) Index Cond: (user_id = 3) (2 rows)

Запросу нужен только user_id, а он уже есть в индексе — таблицу можно не читать совсем. Это covering-эффект: width=4 вместо 24. Добиться его для более широкого набора колонок помогает INCLUDE (см. раздел 04).

Index Scan Backward: порядок и LIMIT

ref_sql_index_lab.sqlsql
EXPLAIN SELECT * FROM orders_big
WHERE created_at >= '2024-03-01'
ORDER BY created_at DESC
LIMIT 10;
QUERY PLAN --------------------------------------------------------------------------------------------------------------- Limit (cost=0.29..0.65 rows=10 width=24) -> Index Scan Backward using idx_orders_big_created on orders_big (cost=0.29..480.31 rows=13601 width=24) Index Cond: (created_at >= '2024-03-01 00:00:00'::timestamp without time zone) (3 rows)

Сортировки в плане нет: индекс по created_at читается в обратную сторону, а LIMIT останавливает чтение после десяти строк. Так «последние N» работают без полной сортировки таблицы.

Функция и приведение ломают индекс

ref_sql_index_lab.sqlsql
EXPLAIN SELECT * FROM orders_big
WHERE created_at::date = DATE '2024-01-02';

EXPLAIN SELECT * FROM orders_big WHERE id::text = '4242';
QUERY PLAN ---------------------------------------------------------------- Seq Scan on orders_big (cost=0.00..2137.00 rows=500 width=24) Filter: ((created_at)::date = '2024-01-02'::date) (2 rows) QUERY PLAN ---------------------------------------------------------------- Seq Scan on orders_big (cost=0.00..2387.00 rows=500 width=24) Filter: ((id)::text = '4242'::text) (2 rows)

Оба раза — Seq Scan, хотя индексы на created_at и id есть. Причина в Filter: условие применяется к результату функции/приведения, а индекс хранит исходные значения. Это называется «условие не sargable».

JOIN-план

ref_sql_index_lab.sqlsql
EXPLAIN SELECT o.id, u.name
FROM orders_big o JOIN users u ON u.id = o.user_id
WHERE o.user_id = 3;
QUERY PLAN ---------------------------------------------------------------------------------------------- Nested Loop (cost=227.29..1315.36 rows=20000 width=9) -> Seq Scan on users u (cost=0.00..1.06 rows=1 width=9) Filter: (id = 3) -> Bitmap Heap Scan on orders_big o (cost=227.29..1114.29 rows=20000 width=8) Recheck Cond: (user_id = 3) -> Bitmap Index Scan on idx_orders_big_user (cost=0.00..222.29 rows=20000 width=0) Index Cond: (user_id = 3) (7 rows)

Соединение на маленьком users — через первичный ключ, на большой orders_big — через Bitmap Heap Scan. Порядок в плане читается снизу вверх: сначала одна сторона, затем для каждой её строки — поиск по индексу другой.

Заказы пользователя: WHERE user_id = 3

ref_sql_index_lab.sqlsql
EXPLAIN SELECT * FROM orders_big WHERE user_id = 3;
QUERY PLAN ---------------------------------------------------------------------------------------- Bitmap Heap Scan on orders_big (cost=227.29..1114.29 rows=20000 width=24) Recheck Cond: (user_id = 3) -> Bitmap Index Scan on idx_orders_big_user (cost=0.00..222.29 rows=20000 width=0) Index Cond: (user_id = 3) (4 rows)

Планировщик выбрал Bitmap Heap Scan: 20 000 строк — это пятая часть таблицы. Индекс idx_orders_big_user участвует, но читает страницы пачкой через битмап. Если нужен более узкий срез, добавьте условие по дате — тогда доля строк упадёт.

Последние 10 заказов

ref_sql_index_lab.sqlsql
EXPLAIN SELECT * FROM orders_big
ORDER BY created_at DESC
LIMIT 10;
QUERY PLAN ----------------------------------------------------------------------------------------------------------------- Limit (cost=0.29..0.62 rows=10 width=24) -> Index Scan Backward using idx_orders_big_created on orders_big (cost=0.29..3244.29 rows=100000 width=24) (2 rows)

Обратный Index Scan по created_at плюс LIMIT — чтение десяти строк вместо сортировки ста тысяч. Обратите внимание на cost внешнего узла: он почти нулевой, потому что оценка ограничена лимитом.

Отчёт по пользователям: EXPLAIN запроса с join

ref_sql_index_lab.sqlsql
EXPLAIN SELECT u.name, COUNT(*) AS orders
FROM orders_big o JOIN users u ON u.id = o.user_id
GROUP BY u.name
ORDER BY orders DESC, u.name;
QUERY PLAN -------------------------------------------------------------------------------------- Sort (cost=2623.22..2623.23 rows=5 width=13) Sort Key: (count(*)) DESC, u.name -> HashAggregate (cost=2623.11..2623.16 rows=5 width=13) Group Key: u.name -> Hash Join (cost=1.11..2123.11 rows=100000 width=5) Hash Cond: (o.user_id = u.id) -> Seq Scan on orders_big o (cost=0.00..1637.00 rows=100000 width=4) -> Hash (cost=1.05..1.05 rows=5 width=9) -> Seq Scan on users u (cost=0.00..1.05 rows=5 width=9) (9 rows)

Когда нужны все строки, а не выборка, индексы не помогают: план честно читает обе таблицы (Seq Scan) и соединяет через Hash Join. HashAggregate считает COUNT(*) по группам, Sort упорядочивает результат. Это нормальный план отчёта.

07Пять ошибок, на которых спотыкаются

Функция на колонке в WHERE

WHERE created_at::date = DATE '2024-01-02' и WHERE lower(name) = 'anna' не используют обычный индекс: условие применяется к результату выражения. План — Seq Scan (раздел 05).

Переписать в диапазон по колонке (created_at >= ... AND < ...) или создать индекс по выражению: CREATE INDEX ... ON orders_big ((created_at::date)).
Ведущий % в LIKE

LIKE '%anna%' ищет подстроку в любом месте, а btree умеет только префикс и то не всегда: в локали en_US.UTF-8 нужен индекс с text_pattern_ops. Обычный индекс такой запрос не ускорит.

Для подстроки — pg_trgm и GIN-индекс, либо полнотекстовый поиск. Для префикса — индекс с text_pattern_ops.
Ждать индекс при низкой селективности

Индекс на user_id есть, но WHERE user_id BETWEEN 1 AND 5 пропускает все строки — Seq Scan дешевле. В лаборатории этот запрос так и планируется.

Проверяйте долю строк: индекс нужен для узкого среза. Расширяйте условие датами/статусом, а не «всеми значениями».
Приведение типа в условии

WHERE id::text = '4242' читает всю таблицу: индекс хранит integer, а сравнивается текст. Та же история с датой и строкой.

Сравнивайте в родном типе: WHERE id = 4242. Приведение — только если оно есть в индексе.
Индексы «на всякий случай»

Каждый индекс замедляет INSERT/UPDATE и занимает место. Индексы-дубликаты и индексы, которые никто не выбирает, — чистая стоимость записи без выгоды чтения.

Держите индексы под реальные запросы; лишние удаляйте. Использование видно в статистике вроде pg_stat_user_indexes.

08Мини-проверка

Пять вопросов на понимание и две задачи. Сначала своя попытка — потом спойлер.

Чем EXPLAIN отличается от EXPLAIN ANALYZE?

EXPLAIN только строит план по статистике. EXPLAIN ANALYZE реально выполняет запрос и добавляет actual time, rows и loops. Второй вариант нельзя бездумно запускать для INSERT/UPDATE — изменения произойдут.

Резюме: EXPLAIN — оценка, ANALYZE — факт и выполнение.
Почему Seq Scan иногда лучше Index Scan?

Seq Scan читает страницы подряд, а Index Scan прыгает по таблице. Если фильтр пропускает большую долю строк или таблица маленькая, последовательное чтение дешевле. Планировщик сравнивает cost и выбирает.

Резюме: индекс — не всегда быстрее; он выгоден на узком срезе.
Что такое селективность?

Доля строк, которые проходят фильтр. 1% — высокая селективность (индекс выгоден), 50% — низкая (обычно Seq Scan). Оценку планировщик берёт из статистики, которую обновляет ANALYZE.

Резюме: чем меньше строк проходит, тем полезнее индекс.
Что такое covering index и Index Only Scan?

Это индекс, в котором есть все колонки, нужные запросу: таблицу можно не читать. В плане — Index Only Scan. Расширить индекс без смены ключа можно через INCLUDE.

Резюме: всё нужное в оглавлении — в книгу идти не обязательно.
Почему created_at::date = ... не использует индекс?

Индекс хранит created_at, а условие — про created_at::date: это разные значения. Помогает индекс по выражению ((created_at::date)) или переписывание в диапазон created_at >= ... AND < ....

Резюме: не оборачивайте колонку — оборачивайте константу.

02 Последние 10 заказов пользователя

-- ожидается: Index Scan Backward по created_at с Filter по user_id
Показать решение и разбор

EXPLAIN SELECT * FROM orders_big

import bisect
ids = [1, 2, 3]
bisect.bisect_left(ids, 3)

dict отвечает на вопрос «где значение с этим ключом» за O(1), но не умеет «все между 2 и 5» и не хранит порядок. btree-индекс умеет и то и другое — поэтому база выбирает его так часто.
